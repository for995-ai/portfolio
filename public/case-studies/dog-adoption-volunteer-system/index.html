狗狗領養＆志工系統

Dog Adoption & Volunteer Management System

以 PHP + MySQL 從零建置的動物之家管理系統，把狗狗資料管理、 領養申請審核、志工活動報名三條原本分散的流程， 整合在同一套關聯式資料庫與同一個後台之中。專案重點不在前端視覺， 而在資料表關聯設計、跨資料表的狀態同步，以及以 Session 控管的角色權限流程。

問題與動機

小型動物之家在管理送養與志工事務時，常見的痛點是：

  • 資料分散：狗狗基本資料、領養申請單、志工名單分別存放在紙本或多份試算表。
  • 狀態不同步：狗狗已被領養，但公開送養名單沒同步更新，造成重複申請。
  • 名額難以掌握：志工活動人工統計報名，容易超收，也難以避免重複報名。
  • 審核不透明：申請人送出表單後，無法查詢自己的審核進度。
  • 三種資料統一存放於同一個關聯式資料庫，透過 ID 欄位互相關聯。
  • 審核通過時同步將狗狗標記為已領養（dogs.is_adopted = 1），前台清單即時反映。
  • 報名時以 COUNT(*) 比對活動上限 max_people，額滿即擋下，並防止重複報名。
  • 使用者可於「我的領養紀錄」查詢每一筆申請的狀態（待審核／已通過／已拒絕）。

TECHNICAL ARCHITECTURE

Database · 資料庫層
MySQL / MariaDB資料庫 dog_adoption：5 張 InnoDB 資料表

架構特點

  • 無框架的多頁式架構：每個 .php 檔案同時扮演控制器與視圖，頁面開頭先做 Session 與角色檢查，再進行資料查詢，最後輸出 HTML。
  • 伺服器端權限守門：管理員頁面於檔案最上方檢查 Session 中的 role 是否為 admin，未通過即中止執行。
  • 資料庫存取：主要查詢使用 mysqli Prepared Statement 搭配 bind_param()；動態搜尋條件則以陣列累積參數與型別字串後展開綁定（list_dogs.php）。
  • 檔案儲存分離：狗狗照片以 uniqid() 前綴命名後存放於 uploads/，資料庫僅保存相對路徑（dogs.image_url）；刪除狗狗時一併移除實體檔案。
  • 連線設定與程式碼分離：資料庫帳密置於 db.php，不納入版本控制，repository 僅提供 db.example.php 範本。

展示策略

公開 Demo 的目的是完整呈現系統流程，而不是開放一套可任意寫入的正式系統，因此上線前做了以下安全化調整：

09學習與回顧

LEARNING / REVIEW

  1. 關聯式資料庫設計：從真實情境（送養 + 志工）拆解出 5 張資料表，區分主體資料與關聯／交易資料，理解多對多關係需要中介資料表來承載。
  2. JOIN 查詢的實務應用：後台的申請與報名列表需同時顯示帳號、狗狗名稱與活動名稱，實作了兩層與三層的 INNER JOIN 查詢。
  3. 動態條件查詢：list_dogs.php 依使用者選擇的條件動態組合 WHERE 子句與 bind_param() 的型別字串，理解到「動態 SQL」與「參數化查詢」可以並存。
  4. 跨資料表的狀態一致性：審核通過時需同時更新 adoption_requests.status 與 dogs.is_adopted，實際體會到缺乏交易（Transaction）保護時，兩段 SQL 之間存在不一致的風險。
  5. Session 與角色權限控管：以 Session 保存登入狀態，並在每個受保護頁面最上方進行角色檢查，理解「權限必須在伺服器端驗證」，而不是只把前端按鈕藏起來。
  6. 檔案上傳與資料庫的分工：圖片存於檔案系統、路徑存於資料庫，並在刪除資料時一併處理實體檔案。
  7. 資安意識的建立：完成後回頭檢視程式碼，辨識出明碼密碼、缺少 CSRF 防護、以 GET 執行寫入操作等問題，是本專案最重要的收穫之一。
  8. 個資保護與版本控制：將設定檔與真實資料排除於 repository 之外，改以 .example 範本與純結構 schema 對外發布。

10改善方向

FUTURE IMPROVEMENTS

以下為檢視現有程式碼後整理出的優化方向，目前皆尚未實作。

資料庫層

加入 Foreign Key Constraints
schema.sql 未宣告任何 FK，關聯僅靠 ID 欄位與應用層 JOIN 維持；應補上 FK 與適當的 ON DELETE 行為，避免刪除使用者或狗狗後留下孤兒資料。
為關聯欄位建立索引
adoption_requests.user_id / dog_id、volunteer_signups.event_id / user_id 皆為查詢與 JOIN 的常用條件，目前無索引。
volunteer_signups 加上唯一鍵
目前以 PHP 查詢檢查重複報名，若改為 UNIQUE (event_id, user_id) 可由資料庫層直接保證。
以 Transaction 包裹審核流程
「更新申請狀態」與「更新 dogs.is_adopted」為兩段獨立 SQL，中途失敗會造成狀態不一致。
狀態欄位型別優化
adoption_requests.status 目前為中文字串，可改為 ENUM 或狀態碼，避免拼寫不一致。

安全性與驗證

密碼雜湊
目前為明碼儲存與比對，應改用 password_hash() / password_verify()。
重設密碼流程
forgot_password.php 目前直接顯示密碼，應改為寄送一次性重設連結（Token + 有效期限）。
統一使用 Prepared Statement
多數查詢已參數化，但 delete_user.php 與 admin_adoptions.php 部分刪除／更新語句仍以字串串接組成 SQL。
寫入操作改用 POST + CSRF Token
審核通過、拒絕、刪除等操作目前皆透過 GET 連結觸發，應改為 POST 並加上 CSRF 驗證。
補齊寫入端的登入檢查
submit_adoption.php、submit_volunteer.php 直接讀取 Session 中的 user_id，未先驗證是否已登入。
上傳檔案驗證
add_dog.php、edit_dog.php 未檢查副檔名、MIME type 與檔案大小。
輸出一律跳脫
多數頁面已使用 htmlspecialchars()，但 admin_users.php 直接輸出 username 與 role。
表單欄位與資料表對齊
volunteer_signup.php 收集了姓名／電話／備註，但 submit_volunteer.php 僅寫入 event_id 與 user_id；add_dog.php 亦未寫入 health_status 與 description。

前端與工程實務

Responsive UI
目前各頁使用固定寬度與內嵌 <style>，行動裝置瀏覽體驗不佳；應抽出共用 CSS 並加入 RWD。
抽出共用版型
導覽列、頁尾與權限檢查在多個檔案中重複，可抽成 header.php、auth.php 等共用檔案。
部署設定自動化
公開 Demo 已完成部署，但環境差異目前仍以手動調整為主；可將連線設定改為環境變數、補上 .htaccess 與一份可重現的部署說明。
自動化測試
專案目前無測試，可為登入驗證、權限守門與領養審核流程加入 PHPUnit 測試。
錯誤處理
目前多以 echo 搭配 alert() 回報結果，可改為統一的錯誤頁面與 Flash Message 機制。
